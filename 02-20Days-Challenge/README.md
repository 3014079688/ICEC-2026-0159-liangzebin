# 阶段二 · 20 Days Challenge（20 天攻坚）

> 目的：体现**过程**，而不是只交一个结果。评委看的是你每天怎么想、怎么试错。

## 本目录放什么

| 位置 | 内容 | 命名规范 |
| --- | --- | --- |
| `src/` | 源码、固件、脚本、配置文件 | 保持可运行，附 `requirements.txt` |
| `process_logs/` | 每日过程日志 | `Day01.md` ~ `Day20.md` |
| `iterations/` | 版本迭代记录 | `v1.md` / `v2.md` … 或 `2026-10-20-改用ToF方案.md` |

## 每日日志模板（复制到 `process_logs/DayXX.md`）

```markdown
# Day XX ｜ 2026-10-XX

## 今日目标
- 

## 实际做了什么
- 

## 遇到的问题
- **问题**：
- **尝试过的方案**：
- **最终怎么解决的 / 是否解决**：

## 数据与截图
（贴关键输出、日志、测量数据）

## 明日计划
- 
```

> 日志的关键是**记录卡点**。一帆风顺的日志在评审眼里没有信息量，把「试了 A 失败 → 试了 B 失败 → 试了 C 成功」写清楚，反而是加分项。

## 版本迭代记录模板（`iterations/vX.md`）

```markdown
# vX ｜ 日期
## 相比上一版改了什么
## 为什么改（触发原因 / 数据 / 反馈）
## 效果对比（改前 vs 改后，用数据说话）
## 被否决的方案与原因
```

## 提交检查清单

- [ ] `process_logs/` 里日志日期连续，没有长时间断档
- [ ] `src/` 里的代码能跑（附依赖说明）
- [ ] `iterations/` 至少记录了 2 次以上的真实版本差异
- [ ] **每个工作日都有 git commit 记录**（commit 时间本身就是过程证据）
